# Olist 电商订单履约风险诊断与客户体验分析

An end-to-end business analysis of delivery performance, customer reviews and seller investigation priorities using MySQL and Python.

基于 Olist 2016—2018 年巴西电商公开历史数据，围绕**哪里出现履约问题、问题集中在哪个阶段、客户体验如何变化、运营应优先调查谁**展开分析。项目包含数据质量审计、多表订单粒度统一、地区与月份拆解、统计验证和卖家筛查，面向数据分析实习作品展示。

## 业务分析路径

1. **衡量履约现状**：清查订单状态、缺失和时间倒置，用有效已交付订单衡量配送时长与承诺兑现情况。
2. **缩小调查范围**：同时看延迟率与延迟数量，再按月份、配送阶段和卖家所在州拆解地区差异。
3. **验证客户体验关联**：统一评价粒度，比较超期程度与差评率，检查评价规则敏感性，并进行 Logistic 回归。
4. **形成调查名单**：综合卖家订单规模、延迟与差评，用去重的问题订单数量及占比筛选候选，再区分交运和后续配送环节。
5. **补充完整性交付视角**：检查准时订单中的多商品、多卖家结构，避免把系统准时签收等同于客户完整收货。

## 数据与样本口径

数据来自 [Olist Brazilian E-Commerce Public Dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)，原始数据许可为 CC BY-NC-SA 4.0；下载与使用须遵循数据源条款。技术栈为 **MySQL 8+、Python、pandas、NumPy、Matplotlib、statsmodels、PyMySQL**。

| 分析模块 | 样本 | 筛选与分母 |
| --- | ---: | --- |
| 原始订单 | 99,441 笔订单 | 全部订单状态 |
| 整体与地区履约 | 96,470 笔订单 | 已交付；下单、收货及承诺日期有效；收货不早于下单 |
| 平台配送阶段 | 96,281 笔订单 | 另要求下单 ≤ 交承运方 ≤ 收货 |
| 延迟与差评主分析 | 95,299 笔订单 | 有效已交付订单中恰有一条非空评分评价 |
| 单卖家画像 | 95,195 笔订单、2,948 名卖家 | 每订单仅一个不同卖家；其中 94,051 笔有单条有效评价 |
| 单卖家交运诊断 | 95,029 笔订单 | 单卖家样本中交承运方时间有效且顺序合理 |

配送延迟按**收货日期晚于承诺日期**判断；差评定义为 **1—2 分**。配送耗时按秒换算为天，交运超期按完整时间戳判断。不同模块的订单数、评价数和卖家数不混用，详见[方法与指标](docs/methodology.md)。

## 主要发现与业务含义

### 1. 延迟集中在长尾订单，地区调查需要同时看规模和比例

有效已交付订单平均配送 **12.56 天**，中位数 **10.22 天**，P90 为 **23.10 天**；**6,534 笔延迟，延迟率 6.77%**。实际配送达到 21 天的订单占 12.96%，集中了 86.04% 的延迟订单。

SP 有 40,494 笔有效订单、1,820 笔延迟，延迟率 **4.49%**；RJ 有 12,350 笔有效订单、1,495 笔延迟，延迟率 **12.11%**。SP 的问题规模大，RJ 的比例和规模均值得深入调查。

![订单规模最大的十个州的延迟率](figures/state_delivery.png)

### 2. RJ 的问题需要沿月份与交运后阶段继续追查

2017 年 11 月至 2018 年 3 月，RJ 的 4,351 笔有效订单中有 1,150 笔延迟，延迟率 **26.43%**。在时间顺序有效的阶段样本中，RJ 交承运方后平均耗时由前期的 **9.66 天**升至 **17.70 天**，交承运方前由 3.35 天升至 3.74 天。变化主要体现在后续配送阶段，提示优先调查相关时期的目的地、运输链路与承诺时限，现有数据不能直接确定责任方。

图中前期为 2017 年 9—10 月，高延迟期为 2017 年 11 月—2018 年 3 月，后期为 2018 年 4—6 月；每根柱标注各自阶段有效样本量。

![RJ和SP不同时期配送阶段](figures/regional_stages.png)

### 3. 延迟越严重，观察差评率越高

在 95,299 笔单条有效评价订单中，延迟订单差评率 **62.36%（3,962 / 6,353）**，准时订单为 **9.25%（8,227 / 88,946）**。延迟 1—3 天、4—7 天及 8 天以上的差评率分别为 **32.14%、67.53%、79.31%**。

| 统计量 | 估计值 | 95% 置信区间 |
| --- | ---: | --- |
| 未调整差评率差 RD | 53.11 个百分点 | 51.90—54.31 个百分点 |
| 未调整风险比 RR | 6.74 | 6.56—6.93 |
| 调整后优势比 OR | 14.78 | 13.94—15.66 |

回归调整客户所在州和下单月份，标准误按 `customer_unique_id` 聚类。OR 衡量优势比，不能解释成差评概率增加 14.78 倍；未调整 RD/RR 区间未按客户聚类。以上均为**观察性关联**，未控制商品质量、价格、卖家服务等全部潜在混杂因素。

![不同超期程度对应的差评率](figures/review_rate_by_delay.png)

### 4. 用问题规模与比例形成卖家调查名单，再区分环节

以单卖家样本的订单加权延迟率 **6.85%**、有效评价差评率 **12.33%** 为探索基准，201 名至少有 100 笔订单的卖家中，55 名双指标偏高。分别取去重问题订单数量前 5 名、问题占比前 5 名，合并得到 **9 名优先调查候选卖家**。问题订单是“延迟或差评”的并集，重复情况只计一次。

提高最低订单量至 150 笔后保留原名单 8 人，降至 50 笔后保留 7 人，说明名单有一定稳定性，也依赖探索阈值，不能认定 100 笔是最优门槛。

![卖家延迟率与差评率四象限](figures/seller_risk_quadrants.png)

95,029 笔有效交运订单中，有 6,518 笔最终延迟，其中 **4,706 笔（72.20%）已按时交运**。因此应分别核查备货交运与后续配送；同时，交运超期组最终延迟率约 20.94%，按时交运组约 5.45%，不能据此忽视交运环节。

单卖家样本中 14,165 笔可观察问题订单涉及商品金额及运费合计 **R$ 2,564,540.84**。该值用于衡量涉及的交易规模，**不代表实际损失、退款或可挽回收益**。公开候选表使用展示编号，未发布订单和客户明细。

![最终延迟订单的交运情况](figures/handoff_diagnosis.png)

### 5. 准时送达不能完整代表商品交付体验

88,946 笔准时且有单条有效评价的订单中，单商品单卖家、多商品单卖家、多商品多卖家的差评率分别为 **7.53%、20.99%、47.17%**。进一步限定恰好两条商品明细，单卖家组为 **19.69%（1,173 / 5,956）**，双卖家组为 **45.68%（423 / 926）**。

原项目的少量人工评论阅读提供了部分未收货、少件、错发等调查线索，但未形成可复现的全量文本分类，不能将其解释为总体投诉占比或确定原因。业务上应补查商品及包裹层面的完整交付记录，而非仅依赖订单级签收状态。

## 调查建议与局限

- **地区与链路**：优先检查 RJ 高延迟期的交运后时效、目的地及承诺日期变化，并兼顾 SP 的延迟订单规模。
- **卖家分场景排查**：交运超期比例高的候选核查备货和交接；已按时交运但最终延迟较多的候选核查配送链路；准时仍差评的候选补查商品一致性、完整性和售后。
- **验证业务假设**：结合包裹轨迹、售后及补发记录确认原因后，再设计小范围试点与效果评估。

这是基于公开历史数据的个人分析，未在真实企业实施干预；候选名单不构成违规认定或履约责任结论。仅分析已交付订单会遗漏未完成订单风险；评价覆盖有选择性，订单级时间戳无法反映全部包裹与商品的实际交付过程。时期划分和卖家阈值均为探索性选择。

## 如何运行

环境建议：Python 3.9+、MySQL 8+。在仓库根目录运行：

```powershell
python -m pip install -r requirements.txt
# 先下载九份原始 CSV，并按 docs/data_setup.md 在全新数据库执行 SQL 00—05。
python python/01_export_order_review.py
python python/00_export_seller_tables.py
python python/02_visualize_review_delay.py
python python/03_review_statistics.py
python python/04_seller_risk_analysis.py
python python/05_seller_handoff_analysis.py
python python/06_plot_public_summaries.py
```

连接数据库时交互输入用户名和密码，或自行设置 `OLIST_DB_*` 环境变量。原始 CSV 自行从 Kaggle 下载；`data/` 和 `outputs/tables/` 均不入库。已有公开汇总表可直接用于最后一步绘图。完整顺序、SQL 导入路径配置及导出依赖见[数据准备](docs/data_setup.md)。

本次已复跑 Python 评价图、统计模型、卖家筛选、交运合并，并对照原始 CSV 和已有结果核验关键数字；**未实际运行 MySQL 导入、SQL 分析脚本及数据库导出步骤**。SQL 完成静态检查与已识别执行错误修复，不能等同于数据库端执行成功。详情见[核验记录](docs/validation.md)和[报告核验对照](docs/report_reconciliation.md)。
